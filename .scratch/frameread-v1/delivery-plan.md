编号是一条稳定的默认交付顺序，不是串行锁。前置条件中的 `G-*` 是所属阶段已通过运行检查的必要子能力，`C-*` 是已冻结公共契约，二者不能互相代替；定义见[依赖表](#delivery-dependencies)。只需子能力时，不要求等待提供阶段的全部验收。每个阶段都包含相关客户端、权限、配置、测试、故障和既有功能回归，不把这些工作留给 S12。

### 前置条件的含义

`Blocked by` 只记录未具备便无法正确实现或运行验收的条件。下面的能力门禁须有实际输出和运行断言，不能仅凭 SPEC 已写好就算具备。冻结契约后可以立刻拆分并实现消费该契约的纵向 Ticket；运行验收等待所需真实能力到位，不要求所有模块 SPEC 先齐备。S0 的环境失败只阻塞依赖该环境的路径，其余代码调查、契约澄清和独立实现不被一并锁住。

### 广泛兼容修改的扩展、切换与清理

1. **兼容扩展。** S1/S2/S3/S4/S6 在各自范围采用附加 Flyway 迁移，保留旧成果、旧上下文及可信上传绑定；先登记公共字段/读写条件和测试，不把增列视为阶段交付。原 V1～V3 不改写，不凭文件名/MD5 补造历史身份。
2. **受控切换。** S6 新写启用前核对所有生产者、消费者、目标级读写、SSE、反馈关联和重放调用方。旧键只在载荷能唯一证明完整作用域时迁入；旧在途消息只接续已核实受理。先切换旧生产者/消费者，再启用新写；无法证明的记录保留诊断，不作为有效结果。S4/S5 的材料和索引新写同时校验 C-M 与适用提交授权。
3. **收尾核查。** S8/S10 验证所有入口已切换，S12 汇总旧数据、失败消息、孤立对象与缓存证据。清理限于已证明失效的临时投影/本次无引用资源；不得删除仍需兼容的旧读、历史成果或未知归属资源，不以全量清缓存解决隔离问题。兼容读是否可以退役须另有证据和授权，本计划不预先批准破坏性清理。

<a id="development-rules"></a>
## FrameRead V1 切片使用方式与执行流程

通用原则与简明流程以[项目 AGENTS.md 的 AI Coding 工作流](../../AGENTS.md#ai-coding工作流)为准。本节说明它们在 S0～S12 中的具体使用方式。

### 选择切片与固定契约

执行顺序为：**选择当前可推进的 S 切片 → 确定所需模块契约 → Grill 澄清未决设计 → 固化模块 SPEC → 检查跨模块集成契约 → 拆分纵向 Implementation Ticket → 编码、测试、审查 → 切片运行验收 → 更新进度**。纯复现/验收阶段不为套流程虚构业务编码 Ticket。

每次会话先读本表的当前阶段、真实 `Blocked by`、阶段记录、已冻结模块契约和相关 Ticket。检查契约是否仍适用于当前代码、配置和调用方；适用就复用，不重新发明开发顺序。模块依赖用于找先要稳定的公共面，切片依赖用于判断本次能实现和验证什么。只有真正影响目标或冻结契约的变化才重新请求决策。

### Grill 与模块 SPEC

Agent 必须先读冻结文档和相关源码，用调查解决事实问题。仅对影响当前切片正确性的未决 Interface、状态归属、调用关系、失败行为、事务、并发或测试 seam 调用 `/grill-with-docs`。不重复询问 PRD、全局 SPEC、ADR 或已冻结模块决定，不对整个产品重做大规模需求访谈。Decision Ticket 01 保持未决，直到形成可追溯 Answer；不能为了编码而自行假设其答案。

用 `/to-spec` 将确认结果归入相应模块 SPEC：职责和 Interface、权威状态/数据、输入输出/错误/不变量、持久化/事务/并发、模块交接、实现决定及测试策略。细化全局架构，不重复设计整个系统，不修改产品范围。按需逐步冻结，登记版本及当前切片使用的公共面。第一个公共契约一旦稳定，相应纵向 Ticket 前置具备即可开始实现，同时继续下一个依赖模块的澄清。

每个跨模块切片都须能定位一段简短集成说明，覆盖端到端顺序、输入输出、数据所有权、关键状态、事务、失败恢复及整体验收。优先在公共模块 SPEC 中引用已有交接约定；仅当这些文档不足以表达整体关系时另建独立集成契约，不重复定义同一规则。模块详细 SPEC 和未来 Ticket 沿用[本地目录约定](../../docs/agents/issue-tracker.md)，生成时登记实际路径，本次不创建占位规格或 Implementation Ticket。

### 纵向 Implementation Ticket

使用 `/to-tickets` 拆分已经澄清的切片。每张 Ticket 对应明确用户行为或可观察系统行为，包含真实前置、所属 S 编号、模块契约版本/章节、R3/A3、可失败且可重复的验收条件及实际测试入口，能在一次相对独立的 Agent 会话中完成。不要按数据库、Repository、Service、Controller 或前端单独水平切层。

复用已存在实现，只补齐当前能力所必需的缺口。旧键迁移、材料发布、删除与修订等跨边界行为在同一可验证任务中贯通，不能用“数据库已完成”代表业务可用。Ticket 的 `Status:` 和本地数字 `Blocked by:` 继续按 tracker 使用；用 `Slice: Sx` 标记归属，S 依赖以本路线为准，不把阶段号混成本地 Ticket 号。

### 编码、审查与运行验收

按 Ticket 使用 `/implement`，对行为变化和缺陷采用能复现失败的 TDD/回归检查，结合自动化和 Code Review。沿用现有 Interface 与工具链，不增加任务运行时、中间件或无关重构。相关客户端、工程配置、部署说明和 CI 随业务一起更新；不以最终合验代替中间切片的接口和页面验证。

切片运行验收同时核对真实用户/系统行为，API 与持久状态及资源，正常/关键异常/恢复路径，单元/接口/集成测试，受影响既有行为，以及版本、环境、样本、操作、预期/实际、日志/计数/截图和未解决问题。使用真实接口与浏览器操作验证相关业务；替身、真实模型、真实平台和真实中间件分别标注。不能以 Agent 声称、源码或测试存在、编译/静态检查通过代替运行验收。

已有测试入口为：`server/` 的 `./mvnw.cmd test`（Unix `./mvnw test`）；`client/` 按 lockfile 安装后 `npm test`、`npm run build`；`extension/` 的 `node --test`。配置检查沿 CI 的 `bash -n scripts/dev-up.sh` 与 `docker compose --env-file .env.example config --quiet`。这些命令当前只是已核对入口，本次未执行；具体环境和真实应用/故障/浏览器步骤按 [SPEC §12](../../docs/prototype/SPEC.md#spec-verification)留证。

### 阶段状态、证据与冻结变更

下列是不同证据状态，不是同义词：

| 状态 | 需要的依据 |
| --- | --- |
| 设计已确认 | 决策/Answer 已记录，当前切片无未决的关键设计。 |
| 模块契约已冻结 | 当前要消费的公共面有版本和权威位置，不要求所有模块细节已完成。 |
| Ticket 已实现 | 本 Ticket 的代码与必要文档已落地，关联 diff 可审查。 |
| 自动化测试通过 | 已执行与该代码/依赖/配置相符的检查，记录命令、结果和限制。 |
| 切片运行验收通过 | 本切片出口、关键异常/恢复、回归及真实证据齐备，阻断缺陷已解决；此时才标记切片完成。 |

阶段结束在本表更新当前状态，并在所属切片记录登记实际 SPEC/Ticket/证据路径、代码版本、失败记录、未验证项和下一个可推进阶段。阶段记录复用本地 `.scratch/<feature>/` 约定，实际建立时链接回本表；不复制主表。失败门禁仅阻止依赖它的路径，已有证据在相关代码、依赖、配置及环境未变时可复用。外部阻塞或仅部分通过不能写成完成。

正式冻结后保留 S0～S12 编号及其能力含义。实现细节可在模块 SPEC/Ticket 中细化，不引发重新编号。确需改变阶段范围或依赖时，先记录原因、受影响契约/需求/阶段/证据、新旧映射及计划版本；影响产品或架构基线须另行取得相应变更授权。不得静默移动已验收能力或降低完成条件。后续实施严格依据本表与依赖关系推进。
