# FrameRead V1 产品需求文档

本文是 V1 的产品与验收基线。文中的操作结果均为实现应满足的契约，运行验证留待开发阶段。产品术语见[术语表](../../GLOSSARY.md)。

## 项目目标与业务角色

FrameRead 是用于 AI 应用与后端开发岗位面试的个人工程项目。以一次视频解读为业务主线，交付从链接提交、异步执行、AI 调用到结果持久化、追问、导出和分享的完整应用。面试展示应能沿一次真实请求解释模块为什么这样划分、谁持有任务状态、外部调用失败后如何恢复，并用运行记录验证这些设计。

个人部署者配置服务、提交任务并管理成果。分享访问者通过只读链接查看指定版本的正式文章、全片导图和引用图片。个人自托管、免登录，管理操作和私人问答只在个人入口提供。

交付目标是提供可在部署者本地运行的 Docker Compose 单机应用。Compose 必须包含完整应用（前端、API、Worker）及运行依赖（PostgreSQL、Redis 和媒体处理所需组件），定义数据库与运行数据的持久化，并在首次启动文档中说明配置文件、模型/ASR 服务、密钥和数据库初始化。V1/P1 默认使用本地持久卷；MinIO 或其他对象存储适配仍属 P2，不影响本地部署验收。计划在 GitHub 开源。输入范围为 B 站或 YouTube 单条视频链接，部署者自行配置服务，无需提供视频平台 Cookie。账号、团队协作、平台计费、本地上传、播放列表和批量处理均在 V1 范围之外。

## 从提交链接到交付成果

1. **首次配置。** 部署者打开个人入口，填写模型服务地址、模型名和 API key，可保存多个模型配置；密钥回显脱敏。图文模型可用后即可提交视频，ASR 独立配置。连接失败或模型不支持所需能力时，设置页给出原因。重启实例后配置保留，后来修改默认模型不改变已受理任务的模型选择。
2. **提交链接。** 粘贴一条 B 站或 YouTube 链接，选择模型、解读模式、深度和可选关注点。「完整解读」为默认模式，覆盖全片重要内容，填写关注点会让相关部分讲得更细。「关注点专题」按指定主题组织正文，并说明覆盖和省略的范围。深度调节展开程度，两种模式都生成全片导图。
3. **跟踪任务。** 受理后返回任务 ID，任务页显示排队、运行阶段及结果。关掉页面后可从历史记录重新进入；刷新或断线重连会恢复到服务端已保存的状态。失败时可见失败阶段、原因和已完成章节，草稿标记为「未完成」。只有通过发布校验的正式版本可导出和分享。
4. **打开正式文章。** 从章节目录阅读正文，点击引用截图查看原帧，按时间出处打开原平台视频复核；若转写只能定位到大致区间，界面标示这一精度。全片导图节点可定位到关联章节或原片时间段，即使专题正文省略某一主题，仍能从导图找到它在视频中的位置。
5. **围绕这条视频追问。** 可直接提问、选中原文段落提问或针对截图提问。段落关联当前正式版本和原文，截图关联实际帧。回答区分视频证据、文章解释、一般知识和外部资料；一般知识不挂原片时间。外部资料默认关闭，显式开启后才可检索，引用须保留 URL、标题、读取时间和原文。依据不足时说明缺少什么。同一对话逐轮处理，上一轮结束后可继续，私人问答保留在个人实例。
6. **导出或分享。** Markdown 包含正文、时间出处和全片导图，单文件中的配图依赖对应图片资源。图文 ZIP 将正文和引用图片以相对路径打包，解压后断网可读，回原平台播放仍需联网。两种导出均读取选定正式版本。网页分享另行创建可撤销链接；访问者需能连到部署者的分享入口。见[只读分享的版本规则](../adr/0001-share-a-fixed-article-version.md)。

## 一次提交如何跨模块完成

| 边界 | 系统应如何工作 | 面试时可核对的事实 |
| --- | --- | --- |
| 前端与 FastAPI | API 校验输入、识别已受理请求，对新任务判断容量。在 PostgreSQL 的同一事务保存任务和待投递记录，提交成功才返回 `202` 和任务 ID。前端可立即查询，媒体处理在后台执行。 | 只剩一个等候名额时并发提交两个独立请求，会产生几条任务记录；创建任务后中断投递，任务如何被找回。 |
| 消息投递与 Worker | Celery 通过 Redis 投递任务标识。Worker 向 PostgreSQL 领取执行权，分阶段保存结果。数据库保存任务状态，Redis 消息可能重复，同一正式结果只能发布一次。 | 对照任务 ID、执行尝试和阶段记录，解释重复投递、旧 Worker 晚到时由谁做最终裁决。 |
| 媒体、AI 服务与文章发布 | Worker 获取视频、采用字幕或调用 ASR，把真实截图送入支持视觉输入的模型。LangGraph 仅编排单次文章任务内的规划、分章生成和校验。发布前校验章节引用、时间范围和所引用图片，正式版本与草稿分别保存。 | 一条时间出处对应哪段文本或哪张真实帧；哪次模型调用使用了这张图片；哪次提交产生了正式版本。 |
| 状态查询与下游操作 | 前端通过 API 查询状态快照并接收 SSE 阶段更新。追问引用当前文章、文本或真实帧；导出和分享读取指定的已保存版本。 | 刷新后恢复到哪个阶段；一次问答使用了哪个版本；生成 ZIP、打开分享链接时是否触发新的生成调用。 |

PRD 约定上述行为与取证入口。后续 SPEC 细化模块接口、事务边界、状态机和选型取舍，架构验收时逐项核对其实现。选型依据可追溯至[架构与实施分析](../research/FrameRead_Feasibility_Analysis.md)。

## 文章的内容边界

文章可以用自己的话整理讲述、解释视频中看得见的步骤。即使选择详细解读，正文也只写原片能够支撑的内容。读者主动追问后，回答可以补充片外知识并标明来源类别。私人问答独立保存，正式文章、导出和只读分享均保留原文。见[片外知识与问答的决策记录](../adr/0002-keep-background-knowledge-in-qa.md)。

沿用参考项目的语言默认值：即使视频是英文讲解，文章和问答也默认用简体中文；引用字幕或转写原句时保留所引用文本的语言和时间出处。

## V1 验收标准

五个维度均须通过。每项验收记录注明实现版本、命令或操作步骤、预期结果、实际结果和证据位置。未运行的项目标记为待验证。

开发阶段按依赖顺序逐步完成业务和工程要求。核心闭环跑通不等于完整 V1；完整 V1 须通过本节五个维度以及下方 P1 工程强化验收。

| 维度 | 通过条件 | 验收证据 |
| --- | --- | --- |
| 功能完整性 | PRD 承诺的 V1 功能逐项实现。前端、API、数据库、Worker、AI 服务完成真实联调；B 站与 YouTube 各有成功样本，覆盖字幕与 ASR、两种解读模式、三种追问入口、导出和可撤销分享。 | 功能清单逐项关联运行记录。至少一次从页面提交起，沿任务 ID 查到接口响应、阶段结果、AI 调用和正式文章，再核对离线 ZIP 与只读分享。 |
| 架构合理性 | SPEC 定义的核心模块和接口有对应实现，各模块的职责、依赖方向、状态归属和数据流清晰。审查重复逻辑与不必要的设计，关键选型能说明解决的业务问题和引入的代价。 | SPEC 与实现对照、架构评审记录，以及正常和故障链路各一条。沿同一任务解释 FastAPI、PostgreSQL、Redis、Worker 和文章编排各负责什么。 |
| 工程正确性 | API 参数校验、数据库约束、事务提交与回滚、任务状态流转和异常处理符合契约。关键业务逻辑有自动化测试，相关测试和项目约定的静态检查通过。 | 测试与静态检查的命令和结果；非法输入、同键并发、取消与发布竞争等用例同时断言接口结果和最终持久化状态。 |
| 运行可靠性 | 正常流程与典型异常均能运行。失败可定位到任务、阶段和调用，按设计重试；重复提交、外部 API 超时、Worker 中断和重启均有明确结果。 | 留存故障触发、恢复过程和最终状态，检查是否重复发布、是否保留草稿、旧 Worker 能否覆盖新结果，以及未知的外部用量如何记录。 |
| 可复现与可验证性 | 可在干净环境按部署文档配置服务、通过 Docker Compose 启动、完成数据库迁移并复跑核心流程。配置说明、迁移、日志、测试和部署文档齐备。 | 记录代码版本、环境、启动和迁移命令、样本、真实运行结果和日志索引。真实 AI 联调与可控故障测试分别注明；证据中的凭据脱敏。 |

### P1 工程强化验收

以下三项正式纳入完整 V1 的 P1 验收。每项均记录实现版本、前置数据、命令或操作步骤、预期与实际结果及证据位置；核心闭环阶段通过而未完成本节，不得称为完整 V1。

| 项目 | 可观察行为 | 可执行验收要求 |
| --- | --- | --- |
| 备份与恢复 | 部署者可按本地部署文档备份并恢复 PostgreSQL、正式文件、问答、分享及撤销状态，以及恢复模型配置所需的密钥材料。备份有明确的一致性边界，数据库、文件和密钥材料构成配套备份集；恢复后数据可用性和分享/撤销状态保持不变。 | 准备两份请求数据：一份保留有效分享，另一份先撤销分享；同时创建正式文章及其正式文件、至少一轮问答，按文档的一致性边界备份，并在干净实例恢复同一备份集。验证文章和正式文件可读、可导出，问答历史可查，有效分享仍可访问，已撤销分享的页面和图片仍被拒绝；用原密钥材料启动并解密恢复的模型配置。缺少必需解密材料时必须明确失败，不能以缺省配置继续运行。 |
| 内部运行概览 | 个人管理入口可查看服务与依赖健康、排队数量、待投递积压及最老等待、Worker 心跳、磁盘与存储、失败分类、版本、运行指标和未知外部调用；允许关联必要的任务 ID 或调用 ID 排障。该概览不向公开分享入口提供，也不暴露私有来源 URL、原始字幕/问答、Prompt、外部页面正文、API key、Cookie、session 或分享 token。 | 用一条正常任务和一条失败后恢复的任务，并观察排队、待投递、Worker 心跳、磁盘和未知调用状态变化，核对概览与服务端持久状态一致；从公开分享入口或不满足既有管理入口访问条件的请求访问概览应被拒绝，不因此增加账号登录流程。检查页面、API 响应和日志，确认只含聚合、脱敏信息及必要的任务/调用 ID。 |
| 版本缓存实验 | 必须完成正式文章版本内容或渲染结果的缓存实验，但是否在产品中启用由结果决定。缓存不改变正式版本、分享有效性或资源授权语义，也不保存授权结论。每次通过分享入口读取缓存内容时，仍检查分享有效性和版本绑定；图片读取另查图片 allowlist 和资源状态。未命中、失效或 Redis 不可用时，按显式声明的回源策略读取 PostgreSQL/文件源，不静默返回过期缓存。 | 在固定样本、配置和环境下分别执行无缓存、冷缓存和热缓存对照，记录命中率、延迟、查询次数、执行计划或 I/O、内存成本以及结果和版本一致性，确认读取不触发新的文章生成；验证撤销分享、切换版本和图片状态变化后缓存不能绕过授权，并在 Redis 不可用时验证回源与降级记录。如果没有可复现的净收益，允许产品保持关闭，保存实验记录即可通过本项；“未启用缓存”不视为未验收。 |

## 业务场景与预期结果

### 视频解读任务的排队与受理

执行槽已占满时，新的视频解读请求使用可用的排队名额。受理返回 `202` 和可查询的任务 ID，页面显示「排队中」，执行容量释放后开始运行。等待名额也已用尽时返回 `503`，提示稍后再试，不创建任务或待投递记录。即使此时满额，对已受理请求以同一幂等键和相同输入重发，仍返回原任务 ID。具体容量是实例的可配置参数。

验收时占满执行槽，仅留一个等候名额，同时提交两个独立的新请求。应恰好一个返回 `202`、一个返回 `503`，数据库只新增一项任务和对应的待投递记录。保持满额，重发已受理请求并核对 ID 一致；释放执行槽，按该 ID 跟踪任务进入运行。满额拒绝的请求可在容量释放后重新提交。见[接单决策记录](../adr/0004-bound-video-task-admission.md)。

### 发现解读错误后核对并修订副本

例如，文章把演示的两个步骤写反。读者可选中该段追问「哪一步在先？」，从回答的时间出处回原片确认，再导出 Markdown，在自己的编辑器中修订并发送文件。V1 不提供站内正文编辑或修订稿发布入口。验收时重新打开站内文章、该段的私人问答和原分享链接，三处仍能对应原来的段落；本地修改只出现在读者保存的文件中。

### 首次使用时只配置了图文模型

读者保存可用的图文模型配置后，即可提交视频链接。若尚未配置语音转写服务（ASR），提交前页面提示「有可用字幕的视频可以直接解读；无可用字幕时需要配置语音转写」。

- **视频有可用字幕**。系统使用字幕和真实画面生成文章，全程无需配置或调用 ASR。
- **视频可获取，但没有可用字幕**。任务停止，页面说明原因并提供语音转写设置入口。读者保存 ASR 配置后，可从原任务页启动新任务，沿用原链接和解读选项，使用新配置进行转写。原失败记录保留。仅保存设置不会启动转写，重新发起也无需再粘贴链接或填写关注点。

### 再次提交同一链接时找回已有文章

读者昨天已生成正式文章，今天再次提交同一视频链接，模型配置、解读模式、深度和关注点等解读设置均相同。页面应显示匹配文章的标题和生成时间，默认操作为「打开已有文章」。读者可以直接阅读全文；从发现匹配结果到打开文章，均不启动生成任务，也不产生新的模型费用。生成时间指上一次解读的时间，不能据此断言原视频此后没有更新。

若读者选择「重新解读」，系统才启动新任务。新任务成功后，读者可打开新的正式文章版本；即使新任务失败，原文章仍可阅读，此前发出的分享链接仍指向原版本。

### 纯口播视频可以交付无截图的正式文章

- **给定**一条讲述清楚的纯口播视频，真实画面已送入模型查看，画面没有提供需要用截图说明的信息，讲述本身足以支撑正文。
- **当**读者打开生成结果，**应看到**正式文章、全片导图、可回原片核对的时间出处，以及未引用截图的简短原因，例如「本视频以口播为主，正文未引用截图」。该文章可正常导出和分享。
- **验收反例**：使用一条关键接线步骤仅在画面中展示的教程。若该画面读取失败，系统应指出无法核实的步骤；不得以纯口播为由将该步骤写成已确认事实。

### 中断、取消与恢复

- **输入或媒体失败。** 不支持的链接在提交时提示原因。已受理后遇到视频受限、下载中断、ASR 失败或资源超限，任务页显示所处阶段、原因及可采取的动作。视频时长、下载字节、工作区占用、模型调用与任务时限均受可配置上限约束。无法取得源媒体时停止处理；模型超时导致的章节缺失只能保留草稿。
- **可确认的短暂故障。** 对可安全重试的临时下载错误、服务限流等，在同一任务中记录每次尝试，按预算退避重试。预算或任务时限耗尽后，页面显示失败阶段和最后原因。无效参数、错误凭据直接报告；部署者修正输入或配置后可发起新任务。
- **Redis 投递中断。** 接口已经受理的任务可按原 ID 查到。恢复后由待投递记录和任务状态驱动补投；同一消息多次到达时只允许有效执行者提交结果。验收时分别核对任务状态、执行记录与发布版本。
- **Worker 中断。** 已持久化的章节和阶段结果仍可查看。恢复执行时只复用输入、配置和来源一致的已完成阶段；失去执行权的旧 Worker 不得改写结果。最终应能追踪每次尝试和唯一的发布结果，或明确的失败原因。
- **部署者取消。** 排队任务可直接取消；运行中先显示已请求取消，再以持久化状态确认结果。若发布先完成则保留成功版本，若取消先成立则禁止发布。已发送的外部调用仍可能产生费用。
- **外部模型超时。** 请求已发出后连接中断，且供应商无法查询结果、也不保证幂等重发时，本地任务以失败结束。原调用结果和用量记为未知，已完成的阶段与草稿保留。任务页说明「上次请求可能已计费」，只有部署者主动重试才创建关联原任务的新任务。新任务复用仍有效的已完成阶段，保留原调用记录，每次新发送单独记账。见[模型结果未知时的重试决策](../adr/0003-retry-an-unconfirmed-model-call.md)。
- **导出失败。** ZIP 引用的正式图片缺失或内容校验失败时，报告具体错误，避免交付缺图的离线包。纯口播文章本来就没有引用图片，可照常导出。
- **公开访问与撤销。** 分享入口只返回绑定版本的文章、导图和正式引用图片。通过公开入口访问配置、任务、私人问答、草稿、原始字幕或尝试触发生成，服务端均应拒绝。撤销后重新请求页面和图片都被拒绝，访问者此前自行保存的副本仍在其设备上。
- **重启与文件清理。** Docker 重启后，模型配置、任务、正式成果、问答和分享状态仍可查询。文章、导图、字幕、正式截图及私人问答长期保留；原视频、音频和临时文件按配置清理。清理后已发布图文仍可读取、导出。追问需新画面时，尝试恢复并验证来源；即使 URL 相同，无法验证同源也应报告不能补看，已有证据保持原样。

## 真实运行后的优化实验

主链真实跑通并取得基线后，再从日志与测量数据中选一个可复现的瓶颈。例如，只有阶段耗时表明取帧是主要等待来源时，才把取帧作为优化对象。记录瓶颈出现的条件、指标定义、环境、样本、配置和复现命令，说明选择改动的依据；改动后用相同条件复测，保留优化前后的原始结果、波动和功能回归结果。面试材料引用实测数字，并注明适用条件。
