# FrameRead 文档与源码审查任务书

本任务书用于复核 FrameRead 的完整产品、Java 后端、Vue Web、浏览器扩展和工程运行资料。正式需求入口是 [PRD V3](../prototype/PRD.v3.md)，正式技术契约是 [SPEC](../prototype/SPEC.md)。研究报告提供事实、风险和验证线索，不能替代正式规格。

## 1. 审查目标

审查者需要回答以下问题。

1. 当前源码、配置、测试和运行脚本是否覆盖 PRD 的完整功能地图。
2. Java/Spring、MySQL、Redis/Redisson、RocketMQ、MinIO、Qdrant、LangChain4j、Vue 和扩展之间的职责边界是否清楚。
3. 视频导入、字幕/ASR、VideoContext、检索、Agent、结构化报告、追问、异步恢复和导出是否形成可追踪闭环。
4. 权限、用户归属、来源固定、同源复用、重复提交、确认未知、过时写回、删除清理和 SSE 重连是否有可验证边界。
5. 文档是否把代码存在写成运行通过，把设计目标写成已实现，或把参考对象的能力边界误写成 FrameRead 的产品契约。

审查不修改业务目标，不重启已冻结的产品决策，不把实现过程写入正式产品文档。需要改变 PRD 或 SPEC 的事项先在审查记录中指出，再由主任务决定是否更新正式规格。

## 3. 现行产品契约

FrameRead 是完整的视频理解与 AI Agent 应用。产品包含注册登录、媒体归属、普通和分片上传、视频链接导入、字幕与 ASR、OCR/关键帧、分块与混合检索、GENERAL/LEARNING/REVIEW/CREATION 四模式和 AUTO 路由、结构化 Markdown 报告、时间证据、连续追问、反馈、计划修订、RocketMQ 异步处理、Checkpoint、SSE、失败台账、管理员重放、Markdown/TXT/MP3 导出、Vue Web、浏览器扩展和 Compose 运行。

V3 输入增强包括 Bilibili 与 YouTube 单视频识别、规范化来源、平台字幕自动选择和无可用字幕时的 ASR 回退。字幕有效时不重复转写。来源原文、时间区间、类型和语言只写入能够观察或证实的信息。

结构化视频分析报告是核心成果。模式化 Section 不是独立文章章节，产品不建立独立文章运行时、公开分享、文章版本发布或全片导图发布系统。报告、转写文本和音频导出属于产品范围，媒体已保存与分析已完成保持不同状态。

异步执行使用 RocketMQ、Redis/Redisson 和目标级 Checkpoint。202 表示受理，具体状态以持久记录和有效执行代次为准。未知模型调用结果不当作零费用或未执行，自动重试受预算和失败分类约束。

## 4. 审查方法

### 4.1 入口与数据流

从 `controller/`、`consumer/`、`service/`、`repository/`、`mapper/`、`entity/`、`dto/` 和 `client/src/` 找到入口，绘制实际调用链。确认 HTTP/SSE、RocketMQ、数据库、对象存储、缓存、向量检索和模型调用的边界。不要只依据目录名推断职责。

### 4.2 状态与事务

检查媒体归属、上传会话、分析作用域、Checkpoint、失败记录、重放代次、锁或租约、删除标记、对象引用和状态查询。重点验证短事务的持久条件、对象存储写入与数据库提交的先后、重复消息、确认丢失、执行者接管和过时写回。

### 4.3 来源与证据

检查链接规范化是否保持平台/视频/分 P 身份。检查字幕候选是否同源、非空、有时间信息，回退 ASR 是否可诊断。检查 OCR/帧、检索命中、报告时间证据和追问引用是否使用真实材料。地址、占位字符串和缓存命中不能被当作图片像素或真实证据。

### 4.4 客户端与恢复

用 DOM、无障碍树和网络记录核对登录、上传、导入、选择模式、启动分析、刷新、SSE 重连、读取报告、追问、导出和扩展跳转。页面刷新只恢复相同作用域，不能自动新建分析。检查正常、空数据、加载、失败和权限拒绝状态。

### 4.5 运行与性能

先验证 Compose 配置、应用启动、Flyway、健康入口和日志，再接入真实中间件、真实平台和模型。记录环境、样本、输入规模、耗时、资源、错误和未验证窗口。只有真实主链出现可复现瓶颈时才做优化实验。

## 5. 输出格式

每份研究文档应保留以下结构。

1. 审查对象、版本线索和范围。
2. 可核对的源码或配置事实。
3. 与 PRD/SPEC 的对应关系。
4. 风险、缺口和需要实施的最小修复。
5. 已运行验证、未运行验证和外部依赖。
6. 不改变现行产品契约的后续建议。

建议表格使用“问题、证据、影响、处理边界、验证方法”列。把“代码存在”“测试存在”“静态推断”“运行通过”分开写，保留失败原因和环境条件，不用空泛的质量形容词。

## 6. 一致性与边界检查

研究资料中的 FrameRead 技术描述统一回到 Java/Spring/Vue、当前 PRD 和当前 SPEC。参考项目的真实技术词只在对应对象的事实审计中保留，并明确其不改变 FrameRead 的产品范围。

研究资料只描述最终产品、当前设计、可核对证据和验证状态。岗位证据文档可以分析 Java 后端岗位的技术相关性，但社区样本属于目的性样本，不能推导市场采用率、招聘结果或已取得的项目指标。

## 7. 完成标准

审查完成时，所有负责文档的 FrameRead 描述与 PRD V3、SPEC、GLOSSARY 和 ADR 一致；参考项目事实与 FrameRead 设计清楚分开；每条重要判断有路径、配置、测试或明确的未验证标签；没有把静态核对写成运行验收。
