## 3. 已确认的产品契约

### 3.1 部署、身份与配置

- 计划在 GitHub 开源，由每个使用者自行 Docker 部署，个人使用。
- 部署后无需注册或登录，填写必要的 API 配置即可使用；不要擅自增加账号、多租户、计费或团队协作体系。
- 首次打开提供设置页，填写模型服务地址、API key 和模型名称；支持保存多个模型配置，后续可选择。
- 配置保存在自己的实例中，Docker 重启后保留。ASR 独立配置；外部资料功能的服务按需配置。环境变量是可选入口，不是唯一入口。
- 这里的 API key 是部署者给个人实例的配置，不是面向多个账号的密钥托管平台。
- 不直接照搬 VidLens 的管理员登录及完整模型运营后台。

### 3.2 输入与典型场景

用户经常观看 B 站和 YouTube 的技术讲解、科普、课程、操作教程，通常十几至几十分钟。问题是看完容易忘、难以定位某句话/PPT/演示画面的时间，纯文字摘要丢失视觉信息。

- 输入视频链接，可选择模型、解读深度和关注点。
- B 站与 YouTube 都是目标成品要求，不沿用“只承诺一个平台”的旧范围。
- 不要求用户提供任何视频平台 Cookie，不以导入浏览器登录态作为前提。
- 字幕优先；缺失时进行语音转写。
- 不继承固定 20 分钟、300 MiB 等未经验证的旧上限。仍需合理资源上限，但应根据目标场景、服务能力和验证方案论证。
- 无平台 Cookie 不等于所有链接必然可获取。明确支持域与受限链接的错误；ASR 不能解决音视频本身无法取得的问题。
- 本地上传、播放列表、批量视频不是已确认要求，不自行增加。

### 3.3 文章、导图与证据

目标产物是一篇带章节目录、内容有时间出处、嵌入原视频真实画面的图文文章，以及一张全片内容导图。用户可以通过阅读获取视频主要内容，并按时间回原片复看。

已确认两种模式：

1. **完整解读，默认**：覆盖全片的重要论点、步骤、示例和必要画面，省略口头重复；关注点使相关内容展开得更细，不能悄悄省略其他重要内容。
2. **关注点专题**：围绕关注点组织文章，可以省略其他内容，但必须说明范围与省略情况。

解读深度用于调节展开程度。全片导图仍覆盖全片，不能因为专题文章省略了章节，就退化为仅覆盖专题的导图。

视频来源内容应可回溯到相应时间段；真实截图必须实际进入模型视觉输入，不能仅传图片路径。画面无法辨认或材料不足时明确标注，不能补造证据。

“代替看视频”是产品使用目标，不得据此宣称逐句无损还原、语义完整率 100% 或已经达到某种准确率。准确率和覆盖效果需要后续样本验证。

文章自动补充视频外知识尚未被明确要求；不得默认把模型常识混入原片叙述。问答中的补充规则见下一节。

### 3.4 阅读中追问

- 支持围绕视频及文章追问，明确一般提问与选段/选帧上下文如何进入问答。
- 默认允许模型补充一般知识，但必须区分视频证据与额外解释，额外解释不能挂视频时间戳冒充原片内容。
- 用户明确开启后，可以获取外部资料并提供可追溯来源。未开启时不自主外查。
- 一般知识未经外部核实不能被标为已验证事实；搜索摘要不能直接冒充已读取原文。
- 问答记录属于个人数据，不随只读文章分享。

### 3.5 导出与只读分享

- Markdown 至少包含正文、时间来源和导图。
- 图文 ZIP 包含 Markdown 与本地图片，解压后可离线阅读；回原视频播放仍需要网络。
- 单个 `.md` 文件没有被要求自包含所有图片；说明其实际图片展示方式，不声称它等同于离线图文包。
- 导出使用已保存的正式结果，不应为了导出再次生成文章。
- 分享链接指向部署者自己的实例，对方能访问该实例时才可阅读；默认本地 Docker 运行不自动提供公网可达性。
- 需要分享时，由部署者配置局域网或公网访问。文档可说明部署要求，本轮不代为部署。
- 分享可撤销，仅公开文章、导图和正式引用图片。
- 分享访问者不能访问配置、创建或控制任务、查看私人问答、查看草稿或修改内容。不要自动公开原视频、字幕原始文件、调用记录和完整处理历史。
- 必须设计免登录个人管理入口与只读分享入口的实际隔离，不能仅在前端隐藏按钮。

### 3.6 数据保留与媒体清理

- 文章、导图、字幕、正式引用截图、问答记录作为长期成果保留。
- 原视频、音频和临时文件可以清理；清理后已生成图文仍应完整可读、可导出。
- 追问需要尚未保存的新画面时，尝试重新取得来源；必须验证恢复的是同一内容，不能仅凭 URL 相同认定身份相同。
- 获取失败或无法确认同源时，明确说明不能补看，不能用新素材静默替换旧证据。
- 具体自动清理周期、磁盘上限不是用户已确定参数，应提出可配置方案与验证方法，避免编造硬指标。

### 3.7 部分失败、草稿与正式成果

- 保留已完成章节、失败位置和错误信息，允许用户查看明确标为未完成的草稿并重试。
- 在来源、配置和依赖仍有效时复用已完成阶段，不要求每次重头生成。
- 草稿不能冒充正式完成；正式分享和导出默认仅使用完整且通过校验的发布版本。
- 材料本身不足可以在完整文章中作为明确限制呈现；这与模型超时导致章节缺失不同。
- 重试、恢复或重新生成不能使已有正式分享链接读到一半更新的内容。

重要事实附 `文件路径:行号` 和函数、类型、表或接口名称。路径与行号以本轮检查为准。

### 5.2 旧报告哪里需要修正

根据已确认需求，形成一套推荐架构和必要的局部替代方案。架构要同时覆盖成功路径、失败路径、恢复与成果长期可用性。

## 6. 必须深入审查的架构与逻辑问题

### 6.1 工作流、任务与恢复的职责

- 分清媒体准备、文章生成、问答、发布、导出等业务任务边界。
- 具体评估 LangGraph 在规划、章节生成、取证、审查、定向修订等阶段的价值，不只列框架优缺点。
- 明确 LangGraph State/checkpoint、PostgreSQL 业务状态、Worker 执行权、队列消息各自负责什么。
- 图节点重放、Worker 接管、重复消息、模型超时但结果未知时，是否会重复收费、重复写文件或重复发布？未知用量不能记成零。
- 阶段复用依据必须包含实际影响结果的来源、模式、深度、关注点、模型/策略版本及上游产物，不能仅按 URL 复用。
- Outbox、租约、fencing、dispatcher/reconciler 等是候选机制，不是用户强制指定组件。说明必要性和最小实现，避免重建原项目全部调度框架；同时不能删除必要正确性保障。
- 状态与事件推送、断线刷新、取消、重试和旧响应覆盖需要一致的契约。不要机械沿用“轮询 P0、SSE P1”的旧工期选择。
- 推荐 REST 写接口、GET 权威快照和 SSE 阶段事件；明确持久游标、断线补读、慢消费者、代理缓冲与回退。区分 HTTP/模型流式草稿与正式发布内容；无双向通信需求不增加 WebSocket。
- 分清协程网络 I/O、阻塞 SDK 的有界线程池、媒体子进程和 Worker 进程；跨进程状态靠事务/租约约束，不能用线程安全容器或本地锁替代。读写锁只在实际共享内存场景下论证。
- 运行取消必须表达 cancel_requested 与发布事务的竞争；普通队列 revoke 不等于停止外部调用。自动重试、用户重试和 broker 补投分别定义，总预算不层层放大。

### 6.2 多模态质量、文章模式与问答

- 长视频如何分块、保持上下文和重要内容覆盖？字幕优先、ASR fallback 的质量与时间精度如何表述？
- 真实帧如何选取、传入模型、引用和持久化？图片存在、已传入模型与视觉结论正确是三个不同层次。
- 完整解读、专题模式、解读深度和关注点分别影响什么？是否存在名义上完整却默默丢弃章节的问题？
- 全片导图与专题文章不能强行一一对应。未写入专题文章的导图节点如何链接原视频范围，避免产生失效章节引用？
- 确定性校验与模型审查分别检查什么，如何处理真实信息缺口及定向修订？不要把 JSON/schema 通过当作语义正确。
- 视频内容、文章解释、一般知识和外部资料如何区分；所选段落/帧的归属如何核对；私人 QA 如何保存且不被分享接口泄露？

### 6.3 个人实例配置与免登录分享

- 配置 UI、配置持久化、环境变量的优先级、模型能力检查、ASR 配置、默认模型与多模型选择怎样闭合？
- 区分“支持用户配置模型”与“任何兼容接口都自动支持图像、工具、结构化输出”。不兼容配置应有明确提示和可验证能力边界。
- Provider URL、模型、提示策略等变更如何影响进行中任务和重试？模型身份不能静默切换；密钥轮换与结果语义版本应分别处理，不要求永久保存旧密钥。
- 密钥不应出现在普通 API 返回、日志、checkpoint、分享、导出或前端构建产物中；说明保存和更新方案。
- 免登录管理只面向个人受信访问，分享是受限公开读取。部署监听、代理路由与后端权限检查如何真正区分这两者？不能以“个人项目”为理由公开所有管理 API，也不能擅自改成强制登录产品。
- 分享令牌、文章版本、图片 allowlist、撤销和缓存是否一致？文章页撤销后图片是否仍可直接访问？公开读取是否可能触发模型调用或暴露私人数据？

### 6.4 PostgreSQL、Redis 与文件一致性

- 先核查已有数据模型和可复用语义，再提出最少必要实体；遵守当前项目对新表公共字段、逻辑删除、时间、版本和查询结构的约束。
- 不把“超过两表关联必然不走索引”写成数据库事实。遵守项目查询约束，同时以实际查询、索引和执行计划验证方案为依据。
- 明确业务事务、唯一性、索引、并发更新、发布原子性，以及关系数据与结构化文章 JSON 的边界。
- 既有“11 张表”等数字不是不可改变的要求。新增表必须说明复用不足之处，避免为了框架或术语额外造一套状态系统。
- 任务入队、领取、取消、重试、最终产物提交和 DB/文件写入失败时，是否可能出现成功状态却无成果，或孤儿文件及错误清理？
- Redis 的 queue/cache/临时状态等用途分别说明；存在真实读取缓存时，给出命中场景、失效和一致性方案；没有收益时不强加通用缓存。
- 流程使用 Outbox 与持久事件时，数据模型必须有相应实体或明确复用位置。资产清理需给出引用/读取租约、deleting 状态与发布事务的协调，不能只写“避免竞态”。
- 区分缓存故障回源与硬性配额/容量准入失败；后者不能无限放行。provider 速率限制按真实配额选令牌桶或适当替代，不为学习同时实现令牌桶与漏桶。
- 有限超时/指数退避先落地，同一 provider 持续故障且造成无效调用时再采用冷却/半开熔断；不可将视觉或引用失败降级为虚假成功。
- 将 request/trace/task/attempt/stage/call 的关联贯通队列、Worker 和外部调用，支持故障定位；日志关联与完整分布式 tracing 区分。单机容错实验不能宣称多机高可用。

### 6.5 生命周期、正式发布和导出

- 草稿、正式文章、导图、字幕、截图、QA 和来源版本之间的归属是否明确？
- 是否能安全清理源媒体而保留正式成果？取消、失败、并发导出/分享/问答时是否会误删仍被引用的资产？
- 来源恢复采用什么可验证的内容身份方案？URL 不变但视频变化、不同下载格式、时间偏移等情况如何处理？不能简单假设所有重新下载的字节必然相同。
- 草稿可查看、失败可重试、有效阶段可复用，同时正式版本保持稳定，这些要求是否相互一致？
- 分享和导出是否基于同一套正式发布判定？ZIP 图片、相对路径、时间来源和导图是否完整，缺图时是否明确失败而非输出伪完整文件？
- 单个 Markdown、图文 ZIP、网页分享三者的能力边界是否被准确说明？

### 6.6 自有参考项目与技术复用

VidLens 为用户自有项目，直接以本地源码作为架构、功能和数据流参照。旧报告中的“许可未知、必须独立重写、公开前另求授权”前提已经被用户澄清，应删除，不再重新审议。

分别分析业务规则、工程机制和具体代码的复用价值。React 展示组件按耦合与适配成本复用；后端保留必要语义，结合 Python/LangGraph/PG/Redis 重设计，不逐文件翻译 Go、不复制无关历史兼容层。本轮依然只修改分析文档，不发布代码或修改 VidLens。

### 6.7 岗位价值与规模边界

沿用可追溯的岗位材料，不合并不同样本分母，不把社招要求直接等同实习门槛，不编造招聘效果。

重新说明个人自托管项目能证明的后端能力与局限：无需多租户或大规模线上用户，也可以通过真实任务、事务、故障和完整交付提供工程证据；不能因此声称生产级规模或已有性能收益。
