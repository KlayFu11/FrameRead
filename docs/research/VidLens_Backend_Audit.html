结论

VidLens 的真正业务状态在 PostgreSQL。job_runs、job_attempts、generation_requests、qa_turns、run_events、task_outbox、idempotency、resource_leases、media_assets 和 storage_reservations 共同构成可恢复的控制平面。Redis 主要承担三类职责：Asynq 的任务投递媒介、资源槽位的短期协调键、短 TTL 缓存/限流键。Redis 中没有可单独解释任务最终状态的业务真相；资源申请还要由 PostgreSQL 租约作最后裁决。

核心链路是“数据库事务写入任务和 Outbox，worker 从队列领取后再次向数据库 Claim，数据库以 execution_epoch、lease_owner 和期限 fencing，结果在同一数据库控制事务中发布，SSE 再从数据库视图读取”。internal/store/store.go:58-73 的事务包装会取得 advisory lock 867914031；internal/store/execution.go:13-103 的 Claim、internal/store/execution.go:109-122 的 Heartbeat、internal/store/execution.go:187-239 的 Fail 和 internal/store/execution.go:294-327 的 Step 都把执行状态变化落到 PostgreSQL。这个设计比“Redis status + worker 直接写结果”更容易解释恢复和并发边界，是 FrameRead 重构时最值得保留的部分。

当前实现的主要边界如下：

  • Asynq delivery retry 与数据库业务 retry 是两套机制。前者处理 broker/task delivery，后者由 Store.Fail 根据 transient、失败次数、active budget 和 deadline 决定；不能只看队列重试次数判断业务是否会重跑。
  • 取消是协作式的。API 先把 run 标为 cancel_requested；worker 下一次 Claim、Fail、Suspend 或 Repair 才会将它终止。共享 source run 仍被其他 request 使用时，取消一个 request 不会取消共享 run。
  • 结果发布有数据库原子边界。FinishSource、Publish 和 CompleteAnswer 在 fencing、快照/帧校验、pin、状态更新和事件记录之间保持同一控制事务；文件物理删除仍是事务外的后续清理，因此文件系统异常会表现为 unavailable/清理重试，而不会让数据库凭空回到未完成状态。
  • Redis 资源键不是最终锁。internal/resource/manager.go:43-158 先 SetNX Redis 键，再调用 Store.AcquireResource，后者在 internal/store/resources.go:10-36 中以数据库主键槽位作最终判断。Redis 不可用时资源申请直接失败，不会自动降级到内存或仅数据库模式。
  • SSE 不是 token 流。internal/httpapi/stream.go:146-313 发送 snapshot、activity upsert、reset 和 keepalive；模型流在 worker 内部组装，前端最终通过数据库视图同步状态。

C1. 提交和去重

POST /api/v1/requests 在 internal/httpapi/server.go:275-298 做 session 认证、body 解码、Idempotency-Key 校验后调用 Store.CreateRequestWithInput。成功响应由 accepted 统一生成，首次为 201，命中 replay 为 200 并带 Idempotency-Replayed: true，同时返回 Location 和过期时间（internal/httpapi/server.go:240-273）。

internal/store/requests.go:22-40 的 replay 以 (scope,key) 查询 idempotency：同 hash 返回同一资源；hash 不同返回冲突；过期键返回 410。request 的 scope 是当前 session，retry 会将旧 request 纳入 scope 变化。Schema 的主键是 (scope,key)（internal/store/migrations/001_init.sql:26）。这意味着幂等性是“同一用户/作用域、同一键、同一规范化输入”的语义，不是全局 URL 去重。

CreateRequestWithInput（internal/store/requests.go:49-240）会规范 URL/purpose，冻结配置和输入 hash，按 source identity 和 article spec 处理以下几种情况：

  1. 复用已有 video_sources/source_snapshots，或者创建 source.prepare/source.restore run。
  2. 对相同 source 的 active/completed source 任务做 coalesce；不同 article spec 作为不同 subscriber 计入 admission。
  3. 发现可复用 article 时直接绑定，否则创建/复用 article.generate。
  4. 每个新 run 通过 newRun（internal/store/store.go:294-328）在同一事务写入 job_runs、初始 run_events 和 task_outbox，而不是先返回 API 再异步补一条队列记录。

这套语义的安全边界是：去重只保护 API 写入和数据库 run 创建；它不保证外部下载、模型调用、文件写入天然 exactly-once。模型和外部操作另有 run_operations 的操作键/提交次数记录（internal/store/artifacts.go:411-551），用来避免已完成结果被重复消费，但 provider 本身仍可能在超时后已经执行。

C2. Outbox、入队与领取

Store.Outbox（internal/store/execution.go:338-345）在短事务中最多 claim 10 条未 delivered 记录，并设置 30 秒 claimed_until。Worker.dispatch（internal/jobs/worker.go:175-216）读取冻结的 config/profile，生成 Asynq task type vidlens.run、任务 ID vl:<run_id>:<dispatch_generation>，设置最大 broker retry 25、timeout 和 deadline；只有 enqueue 成功或对同 ID 冲突任务核对 type/payload 后才调用 OutboxResult(..., delivered=true)。broker 错误按 1/5/15/30/60 秒回退（internal/store/execution.go:347-357）。

因此，API 事务提交成功但进程在投递前崩溃时，数据库仍有 Outbox，下一次 dispatch 会补投。重复 dispatch 不会依赖随机 task id，而是通过确定性 task id 和 payload 校验去重。Worker.reconcile（internal/jobs/worker.go:365-389）每 30 秒检查非终态 run；队列状态为 missing 且没有 pending Outbox 时由 Store.Repair 增加 dispatch_generation、重新排队并生成 Outbox（internal/store/execution.go:362-468）。broker 状态为 unknown 时不自动判定丢失，避免把 inspector 暂时不可用误判成业务丢任务；代价是恢复可能延迟。

2026-11-09 定向核对补充：Worker 进程不是只监听一个 run 队列。jobs.New 为 generation、interactive、maintenance、probes 分别创建 Asynq server；generation 的最大 goroutine 数为 MaxVideoConcurrency=64，但真正开始执行仍由 PostgreSQL admission 裁决；interactive 为 1；maintenance 为 1 且映射 maintenance:1、cleanup:2 并启用 strict priority；probes 使用 store.MaxConcurrentProbes（internal/jobs/worker.go:47-87）。同一进程的 dispatch loop 每秒运行，除 durable Outbox 外还会读取数据库中的待导出和模型探测记录；cleanup 任务每 5 分钟以确定性 task ID 投递一次，重复 enqueue 自动去重（internal/jobs/worker.go:136-160、internal/jobs/worker.go:175-215、internal/jobs/worker.go:391-394）。这些队列承担不同工作类型，但 run 业务状态仍在 PostgreSQL。

C3. Claim、租约和并发

Store.Claim（internal/store/execution.go:13-103）在数据库事务中完成这些检查和变更：

  • generation 必须匹配，终态和 waiting_dependency 不领取。
  • cancel_requested 立即进入 canceled 终止路径；超过 deadline 或 queue wait limit 进入 failed。
  • 仍有有效的 running lease 时不重复领取；过期的 running lease 会关闭来源步骤、计 active time、结束旧 attempt、增加 failure count，再决定是否重启。
  • 通过 admitExecution 检查 live execution setting 和全局 pending admission；容量等待不启动 attempt，也不消耗 active/retry budget。
  • 成功领取时递增 execution_epoch/attempt_no，写入 lease_owner、60 秒 lease_expires_at、job_attempts，并把 QA turn 置为 running。

后续写操作必须通过 fence（internal/store/store.go:330-341）核对 run 仍为 running、epoch 与 owner 相同、lease 未过期且 deadline 未到。旧 worker 即使在网络分区后恢复，也不能用旧 epoch 写 checkpoint、step 或结果。Heartbeat（internal/store/execution.go:109-122）刷新数据库 lease 并计 active time；internal/jobs/worker.go:217-329 中的执行循环大约每 10 秒 heartbeat。

并发上有两层限制：

  • jobs.New 为 generation Asynq worker 配置最多 config.MaxVideoConcurrency（当前源码为 64），但真正是否开始执行由数据库 live setting/admission 再裁决（internal/jobs/worker.go:47-87）。internal/jobs/concurrency_test.go:17-140 覆盖运行中把 live limit 从 2 调到 10、再降回 2；降低不会中断已有任务，新任务会 busy 且不消耗 attempt/failure。
  • Store.Tx 每次控制事务取得同一个 PostgreSQL advisory lock 867914031（internal/store/store.go:58-73），使 request/run 状态变更容易串行化，但也给高并发写入带来全局锁竞争和 2 秒事务超时边界。这个锁不是媒体下载/模型调用锁，长耗时工作仍在事务外执行。

资源并发是另一套槽位控制。Manager.Acquire（internal/resource/manager.go:43-158）根据 ai:interactive、ai:generation、asr、ffmpeg、download 等名称申请 Redis TTL 键，再以 Store.AcquireResource 把同一 slot 写入 resource_leases；每 10 秒左右续租 Redis 和数据库，释放时使用 owner compare，避免删除别人的键。DB 端会清理已过期 lease，并以 (resource,slot) 主键防止双占用（internal/store/resources.go:10-55）。internal/store/resource_wait.go:26-167 只记录有实时 holder 证据的等待区间，并合并重叠等待，避免把 stale wait 当成业务进度。

C4. 失败、重试和恢复

Store.Fail（internal/store/execution.go:187-239）先再次 fencing，再根据 worker 传入的 transient、MaxRetries(kind)、active budget 和 deadline 决定：

  • 不满足条件：调用 terminate(..., "failed", failure)，写终态、结束 attempt、释放 pin/reservation 并写事件。
  • 满足条件：关闭来源步骤、写 retry notice、结束 attempt，把 run 置为 retry_wait，递增 failure_count，保存 retry_not_before 和 failure，并清除 lease。

Worker.handle（internal/jobs/worker.go:217-329）负责将 Media/Agent 错误分类；Asynq 的 delivery retry 和 Store.Fail 的业务 retry 分开。internal/jobs/worker.go:330-364 对网络/预算等 transient 代码允许自动重试；若是文章审阅、结构或语义问题，虽然错误对象可能带 CanRetry，分类仍可能令 automatic=false，不会因为队列重试而盲目重复业务生成。服务关闭时 Suspend（internal/store/execution.go:254-293）把可恢复 run 置为约 5 秒后的 retry_wait，并清除 lease。

Store.Repair（internal/store/execution.go:362-468）覆盖以下恢复分支：取消或 deadline 终止；队列等待超时；资源等待 stall；Outbox 长时间未投递；依赖完成后的 wake；broker archived/completed 但数据库没有结果时失败；broker missing 且没有 pending Outbox 时新建 generation/Outbox。它会保留原 deadline 和 failure_count，所以“补投”不是无上限重置预算。waiting_dependency 主要用于 QA 等待 source restore；依赖成功时复制依赖事件后的步骤并重新排队，依赖失败/取消时终止 dependent run（internal/store/artifacts.go:348-395、internal/store/execution.go:430-468）。

C5. 取消语义

CancelRequest（internal/store/requests.go:242-280）在事务内锁住 request，冻结当前 segment 的 through_seq，将 request 标记 canceled、清空 active run，并调用 cancelUnused。只有当该 source/article run 没有其他 active request 或 waiting dependency 时，run 才会标成 cancel_requested；共享 run 仍被其他 request 使用时继续运行。已取消 request 的历史步骤因 watermark 被冻结，后续共享 run 的事件不会污染它的历史视图。

CancelTurn（internal/store/requests.go:492-512）把 QA turn 和 run 标成 cancel_requested；worker 通过 Claim/Fail/Suspend/Repair 终止。也就是说，HTTP 取消成功返回不等于执行线程已经立即停止，前端应等待 SSE/GET view 变成 canceled。测试 internal/store/store_test.go:70-134 专门覆盖共享取消、冻结历史和幂等 replay，但本次未执行。

C6. 结果一致性

source 完成路径在 internal/store/artifacts.go:96-162：FinishSource fencing 后核对视频 hash、快照唯一性、transcript 和 media asset，再 finishRun；之后 bindPrepared（internal/store/artifacts.go:164-241）在同一控制逻辑中把 waiting_source request 绑定到 snapshot，复用/创建 article run，并 pin 视频。

article 发布路径在 internal/store/artifacts.go:255-316：Publish fencing 后核对 snapshot、所有 cited frame 为 ready、frame 属于当前 snapshot、总大小上限，再写 article、pin article 资源、把匹配 requests 置 completed，并完成 generation run。QA 完成路径 CompleteAnswer（internal/store/artifacts.go:318-345）同样核对 frame ready/snapshot、写 answer、清 active turn 后完成 run。

media_assets 的 state 约束是 ready/deleting/deleted/unavailable，storage_key 唯一；Schema 见 internal/store/migrations/001_init.sql:27。数据库 pin/reservation 防止正在引用的 asset 被清理；internal/store/cleanup.go:10-50 说明物理清理在事务外进行并可重试。数据库结果和文件 bytes 因而不是同一原子系统：数据库先记录可验证的 asset/result，文件删除失败会留下清理状态；读取层会再次检查文件/媒体状态并在过期或不可用时返回对应状态。

API、SSE 与前端同步

HTTP 路由在 internal/httpapi/server.go:42-125。request 的创建、查询、取消、重试、article、activity、events、frame 和 conversation/turn 路由都由同一 server 提供；healthz 只检查 PostgreSQL（internal/httpapi/server.go:44-51），不能作为 Redis/Asynq/模型健康的完整证明。写请求还通过 Origin/CSRF/session 校验（internal/httpapi/server.go:151-224）。

RequestView/TurnView（internal/store/views.go:547-600）从 PostgreSQL repeatable-read 视图组装 status、execution、retry、actions、activity 和 stream position。cursor 使用 secret key HMAC，并绑定 session、资源类型和资源 ID（internal/store/views.go:21-60），不能在不同用户/资源之间复用。

events（internal/httpapi/stream.go:146-313）流程为：认证并读取当前 snapshot，解析 Last-Event-ID 或 after cursor，检查 cursor watermark 是否仍可用，按 session:type:id 订阅 Hub，发送初始 snapshot；如果数据库事件正好连续到 seq+1 且 step 的 last sequence 匹配，发送 activity.upsert，否则发送完整 view.snapshot。旧 cursor 已被清理时发送 stream.reset，并要求前端重新 GET；15 秒 keepalive，session 过期发送 auth 事件，终态后关闭。

Hub 由 internal/httpapi/stream.go:28-145 管理，全局上限 100、单 session 上限 4、每通道 buffer 32、每通道约 1 MiB；慢订阅者会被关闭，避免一个客户端拖住所有请求。Hub 每约 2 秒读取数据库视图，而不是把 Redis pub/sub 当事件真相。internal/httpapi/stream_test.go:8-37 覆盖慢订阅者、计数释放、替换订阅和重复 unsubscribe，未运行。

2026-11-09 定向核对补充：运行页的进度不是只显示一个百分比，而是把后端 view 的多个层次组合展示。RunView 同时读取 request 终态、execution phase/status/retry reason、activity.current_step_id、recent_steps、模型调用/发送计数、execution plan、已展示 frame 及 frame availability；再经 ExecutionPlan、ActivityList、FrameTimeline 展示阶段、动作日志、画面时间线，并根据 actions.can_cancel/can_retry/can_read_article 渲染操作（frontend/src/ui/RunView.tsx:69-104、frontend/src/ui/RunView.tsx:243-280）。因此 FrameRead 不宜把后端状态简化成单一 progress: 0..100；至少应保留 status + stage + current_action + retained_result + actions，否则前端无法恢复和解释失败。

对 FrameRead 重构的保留边界

FrameRead 以合理设计和完整业务为前提展示后端工程能力。以下为 Python 重设计建议，不是 VidLens 新增能力；用户已确认 VidLens 为自有项目，可直接参考源码架构和数据流。应保留以下契约：

  1. FastAPI 内部写接口在一个 PostgreSQL transaction 中完成规范化输入、Idempotency-Key hash、task 创建和 durable outbox；返回 task_id 后由 GET 快照或 SSE 读取数据库 view。个人设置接口同样要有配置 revision，密钥只在服务端凭据存储解密。
  2. 用 PostgreSQL 的 tasks、task_attempts、outbox、stage_results 和 task_events 表达业务状态；幂等 scope/key/hash 优先由 tasks 的唯一约束承载，无独立生命周期需求不另建 idempotency 表。保留 generation、attempt、deadline、lease/fence、retry budget 和 unknown 调用账。运行取消先进入 cancel_requested，与发布在同一任务行上裁决；普通线程锁不能保护多进程执行权。
  3. 推荐 Celery+Redis 或等价 broker 只做投递，不让 Redis status 成为业务真相；Worker 领取前后都回数据库 Claim/fence，broker 丢任务由 outbox/reconciler 补投。Worker 方案不是用户硬约束，PG SKIP LOCKED 是可行的减项备选。
  4. 实现 source.prepare → article.generate → publish 与独立 qa.answer；文章发布必须在同一业务事务中校验 snapshot/frame、固定不可变文章版本和导图、写终态。草稿、attempt 和正式版本分开保存。
  5. 分享 token 绑定正式文章版本，公开路由只返回文章、导图和 allowlist 图片；撤销 token 后页面、图片和缓存均失效。导出读取同一正式版本，缺图或 hash 校验失败就是导出失败，不重新调用模型。
  6. 资源槽位优先复用任务/资源租约；若加入 Redis，区分短期协调与 PG 业务执行权。读取缓存故障可回源，保护供应商配额或机器容量的限流/准入失败则应暂停新受限工作，不能统一称为 best effort。媒体清理用持久引用和必要读取租约保护成果，在 PG 短事务内标记 deleting 后再删文件，防止检查引用与实际删除之间的竞态。
  7. 管理端推荐 REST+GET 快照+SSE，task_events 关键事件与状态同事务写入，缺口重新取快照，慢消费者有界断开。个人实例数据按实例归属；独立公开路由集合只允许 token 绑定的正式版本和图片，不需要增加多租户或强制登录。
  8. 超时、指数退避、错误分类和结构化请求/任务/调用关联日志纳入主链；缓存、provider 令牌桶及持续故障熔断需有对应场景和实验，不为关键词同时加入多种锁、队列或限流算法。单机 broker/Worker 故障恢复属于容错证据，不能直接表述为多机高可用。

这样得到的个人自托管项目仍能展示后端岗位关心的状态机、幂等、队列、租约、失败恢复、事件同步和结果一致性，同时避免把 VidLens 的完整媒体处理、模型运营路由、外连策略和全部迁移一次性搬进 Python。更细的 Python 模块拆分属于重构设计，不是本次源码审计的已实现事实。
