# FrameRead 岗位证据与工程能力映射

岗位材料核读日期：2026-11-18。本文用于把已核对的岗位技术要求映射到 FrameRead 的完整产品能力，不替代项目需求或验收。岗位材料是目的性样本，不能推导市场采用率、录用概率或项目指标。

## 1. 结论

FrameRead 适合作为 Java 后端开发岗位的完整项目，核心展示面是视频理解业务中的 API、权限、MySQL 数据、MyBatis-Plus/Flyway、Redis/Redisson、RocketMQ、MinIO、Qdrant、AI Agent、SSE、失败恢复和 Vue Web 协作。产品从视频或公开链接输入开始，经过媒体处理、字幕/ASR、VideoContext、证据检索和四模式 Agent，生成结构化 Markdown 报告，并支持追问、计划修订、导出和管理恢复。

项目交付标准以 [PRD V3](../prototype/PRD.v3.md) 与 [SPEC](../prototype/SPEC.md) 为准。源码路径、测试、日志和真实运行证据形成后，才可以把对应能力写成已完成项目事实。当前报告只表达能力映射和验证要求。

V3 的链接与字幕能力属于完整产品的一部分。Bilibili/YouTube 单视频识别、来源元数据、字幕选择、ASR 回退和时间精度不会改变四模式报告、异步恢复和权限边界。项目不建立独立文章系统、公开分享平台或通用 Agent Runtime。

## 5. 面试展示的工程主线

一条可复现主线应能解释用户请求如何经过权限与媒体归属、视频来源和字幕/ASR、VideoContext、RocketMQ、Consumer、检索、Agent、Checkpoint、SSE 和报告读取。重点故障包括重复提交、字幕候选失败、ASR 部分失败、模型调用未知、消费重投、执行者失联、删除竞争和页面断线。

每个结论都要附场景、输入、环境、预期、实际、日志和剩余限制。并发、缓存、限流和熔断按真实热点和资源约束选择，不为关键词堆叠。不能从单机验证推导高并发生产能力，也不能从代码存在推导稳定运行。

## 6. 与其他 Agent 项目的边界

FrameRead 的主卖点是一个具体视频理解业务的后端闭环。通用 Agent 的模型循环、工具协议、上下文管理或评测能力只有在当前项目中形成视频来源、时间证据、权限、持久化和失败恢复证据时才计入项目能力。两个项目使用相同技术词，不等于重复或共享运行结果。

1. 真实平台下载、字幕选择、ASR、模型视觉输入、RocketMQ/Redis 故障、浏览器交互和部署尚未全部验证前，不能写成已稳定运行。
2. 岗位样本来自有限、目的性材料。技术出现频次不代表招聘权重、市场比例或录用结果。
3. 项目以个人自托管和单机资源为交付边界，不能写成云原生、高并发、生产级 SLA 或企业规模平台。
4. 性能、成本、准确率、恢复时长和吞吐必须使用同一环境、同一输入和原始数据支撑，不能预填提升百分比。
5. 项目能力以最终代码、测试、运行和验收证据为准。
