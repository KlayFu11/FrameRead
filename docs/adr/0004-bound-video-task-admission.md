# 分析提交的作用域受理与恢复合同

## 决策

分析提交、计划修订和管理员重放均按媒体标识、规范化目标及实际模式寻址，访问时校验媒体归属。异步协调的职责以 [SPEC §7](../prototype/SPEC.md#spec-execution) 为准。

- Checkpoint 保存当前受理代次、动作、确认或执行阶段、期限、持有者执行代次、固定输入引用及恢复所需过程；
- RocketMQ 负责提交后的异步消息，Redisson 负责并发锁与租约，Redis 负责活跃状态和通知；
- 有效受理代次得到 broker 确认，或已被消费者持久领取时返回 202。发送结果不明时返回相应 5xx 与业务原因，保留该代次供状态核对或迟到确认；
- 普通重发先检查当前活动工作，再检查同作用域的适用结果。显式修订或管理员重放按条件受理新工作，修订排队时原结果仍持久保存，开始执行时只重置有效作用域；
- 消费、接管、写回和通知都校验作用域、受理代次、执行代次及租约。过时消息、租约失效或媒体已删除时不得覆盖新结果；
- 未领取受理和已领取执行都采用有界期限。期限耗尽后由用户重新提交或管理员按失败记录重放，客户端不自动创建新分析。

外部模型调用的未知结果、有限重试和预算语义依照 [ADR 0003](0003-retry-an-unconfirmed-model-call.md)。

本决策落实 [PRD.v3.md 的 R3-10](../prototype/PRD.v3.md#r3-10-进度失败与恢复) 与 [SPEC.md §7](../prototype/SPEC.md#spec-execution)。

## 影响

- 业务状态以作用域和持久 Checkpoint 为准，不以 Redis、SSE 或单条消息作为唯一事实。
- 受理、消费和恢复必须在消息、锁、租约与数据库写回之间保留可诊断的确认窗口。
- 接口可以继续返回 202 受理结果，但不能把响应丢失、broker 未确认或消费者未领取描述为已经完成。
